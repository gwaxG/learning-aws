Три сквозных правила, на которых ты теряешь баллы
  1. Граница Region. Что живёт в одном Region и что нужно явно копировать или связывать между Regions (ACM, snapshots, S3 CRR, TGW).
  2. Похожие сервисы — разные задачи. Выбирай по тому, что именно перемещается или обрабатывается (серверы, БД, файлы, поток событий).
  3. Готовая функция лучше ручной сборки. «Least operational overhead» = управляемый сервис, а не EC2 или скрипт.

1. Как устроен экзамен

65 вопросов, 130 минут, проходной балл 720 из 1000. Часть вопросов не оценивается (пробные). Формат: один верный из четырёх или несколько верных из пяти и более. Штрафа за неверный ответ нет, поэтому отвечай всегда.

Как читать вопрос

  • Сначала последнюю строку: что просят (MOST secure / cost-effective / least overhead / highest availability).
  • Выпиши ограничения: Region, объём, время, «без изменения кода», «минимум простоя».
  • Отсеивай варианты с выдуманными сервисами или свойствами (Spot volumes, SR-IOV volumes), с ручной сборкой вместо managed и с нарушением ограничения.
  • Из двух рабочих выбирай то, что точнее соответствует слову-ограничителю.
Слова-ограничители
  • Least operational overhead → serverless и managed.
  • Most cost-effective → Spot, Savings Plans, S3 классы, lifecycle.
  • Near real-time / real-time → Kinesis, а не Athena или batch.
  • Without changing the application → решение на уровне инфраструктуры (cache, proxy, gateway).
  • Highly available → минимум 2 AZ. Disaster recovery → другой Region.

2. Фундамент: Regions, AZ и модель ответственности

  • Region — изолированная географическая область, минимум 3 AZ. Данные не покидают Region сами. Выбор: законодательство, задержка, цена, наличие сервисов.
  • AZ — один или несколько дата-центров, соединённых низколатентно. Подсеть всегда в одной AZ.
  • Edge location — точки CloudFront, Route 53, Global Accelerator, Lambda@Edge. Их больше, чем Regions.
  • Global-сервисы: IAM, Route 53, CloudFront, Organizations, WAF (для CloudFront), Global Accelerator. Остальное — regional.

3. Идентичность и доступ: IAM, Organizations

IAM: основы

  • User — долгоживущая личность (пароль, access keys). Group — набор users (в группу нельзя вложить группу, группа не может быть principal). Role — временные credentials через STS, без постоянных ключей.
  • Policy — JSON: Effect, Action, Resource, Condition. Identity-based (на user/role) и resource-based (S3 bucket policy, KMS key policy, SQS, trust policy роли).
  • Для EC2, Lambda, ECS всегда role (instance profile), никогда ключи в коде или AMI.
  • Root: MFA, нет ключей, использовать только для задач, требующих root.
Логика вычисления политик
  1. По умолчанию всё запрещено (implicit deny).
  2. Любой explicit Deny побеждает всё.
  3. Иначе нужен хотя бы один Allow.
SCP и permission boundary только ограничивают максимум и сами ничего не разрешают: итог — пересечение.
⚠ Ты ошибался здесьMFA на группу пользователей и Parameter Store против Secrets Manager. Политика ключа KMS против прав роли: чтобы роль могла использовать ключ, нужны оба — key policy допускает (или делегирует IAM), и IAM-политика роли разрешает.

Кросс-аккаунтный доступ

В аккаунте B создай role с trust policy на аккаунт A; в A пользователь получает право sts:AssumeRole. Временные credentials, без обмена ключами. Для внешних сторон добавляй ExternalId.

Federation

  • IAM Identity Center (бывший SSO) — вход сотрудников во все аккаунты Organization из корпоративного IdP.
  • Cognito — пользователи твоего приложения (User Pool = каталог и токены, Identity Pool = временные AWS credentials).
  • SAML 2.0 / OIDC federation — прямой вход в консоль через IdP.

Organizations и multi-account слабо

Organizations: управляющий аккаунт, организационные единицы (OU) и member-аккаунты. Даёт consolidated billing (общий счёт, объёмные скидки, общее покрытие RI/Savings Plans) и централизованное управление через SCP.

  • SCP — потолок прав для аккаунтов и OU. Не выдаёт права, не действует на management account, действует на root user member-аккаунта. Типичные SCP: запрет выхода из Region, запрет отключать CloudTrail/Config, запрет root.
  • Control Tower — готовая landing zone: multi-account среда по best practice, Account Factory создаёт аккаунты по шаблону, guardrails (preventive = SCP, detective = Config rules), dashboard несоответствий. Ответ на «настроить и управлять multi-account окружением с наименьшими усилиями».
  • RAM — делится ресурсами (подсети, TGW, License Manager configs) между аккаунтами без копирования.
  • Организационный CloudTrail — один trail для всех аккаунтов; Config aggregator — сводный вид соответствия.
  • Delegated administrator — сервис (GuardDuty, Security Hub, Config) администрируется из отдельного security-аккаунта.
Модель «много аккаунтов»Отдельные аккаунты: prod/dev, log archive, security/audit, shared services (сеть). Граница аккаунта — самая сильная граница безопасности и биллинга. Если спрашивают «изолировать» — новый аккаунт, а не новый VPC.
⚠ Ты ошибался здесьВопрос про landing zone с dashboard несоответствия → Control Tower (Account Factory + guardrails), а не ручная Organizations + Config. SCP не даёт прав: без IAM-политики доступа всё равно нет.

Доступ для приложений и ресурсов

  • S3 bucket policy — resource-based, умеет Deny по условиям (aws:SecureTransport, aws:SourceVpce, org id).
  • Presigned URL — временный доступ к объекту от имени создателя.
  • Permission boundary — максимум прав, который IAM-админ может делегировать пользователю/роли.
  • Access Analyzer — находит ресурсы, доступные извне, и неиспользуемые права.
  • Credential report / last used — аудит ключей и паролей.

4. Защита данных и безопасность слабо

KMS и шифрование слабо

  • KMS — managed ключи в HSM. Типы: AWS owned (невидимы), AWS managed (aws/s3, бесплатно, ротация раз в год автоматически, политику не изменить), customer managed (CMK) (ты управляешь политикой; автоматическая ротация включается галочкой, раз в год).
  • Ключ привязан к Region. Для cross-Region — multi-Region keys или повторное шифрование при копировании.
  • Envelope encryption: KMS шифрует data key, data key шифрует данные. Прямой Encrypt в KMS ограничен 4 КБ.
  • Key policy обязательна у каждого ключа; доступ роли = key policy + IAM (или grants).
  • CloudHSM — выделенный HSM под твоим контролем (FIPS 140-2 Level 3), когда нужен полный контроль ключей или требование compliance. Для обычного шифрования хватит KMS.

S3 security

  • Block Public Access (на аккаунт и bucket) — главный выключатель публичности.
  • ACL считаются устаревшими; включай Bucket owner enforced (ACL отключены).
  • Object Lock (WORM): Governance (можно обойти с правом) и Compliance (нельзя никому, включая root). Glacier Vault Lock — то же для vault.
  • MFA Delete при versioning: удаление версий только с MFA.
  • VPC endpoint + bucket policy с aws:SourceVpce — доступ только из твоей VPC.
  • Access Points — отдельная политика на приложение/команду вместо одной огромной bucket policy.

5. Сеть: VPC, DNS, CDN, балансировщики слабо

VPC: строительные блоки слабо

  • VPC — частная сеть в Region (CIDR /16–/28). Subnet — в одной AZ. 5 адресов в каждой подсети зарезервированы AWS.
  • Public subnet = route table с маршрутом 0.0.0.0/0 → IGW и у инстанса публичный/Elastic IP. Private — без маршрута в IGW.
  • IGW — двусторонний доступ в интернет для public subnet (горизонтально масштабируемый, без ограничений полосы).
  • NAT Gateway — исходящий IPv4 из private subnets. Живёт в public subnet (с Elastic IP), маршрут private → NAT. На AZ свой NAT для HA. Входящие соединения из интернета не пропускает.
  • Egress-only IGW — то же для IPv6 (исходящий да, входящий нет). У IPv6 нет NAT: адреса публичные.
  • Bastion host / SSM Session Manager — вход в private instances; Session Manager без открытых портов и ключей.
  • Flow Logs — метаданные трафика (в S3, CloudWatch); не содержимое.
⚠ Ты ошибался здесь«Исходящий IPv6 из private subnet, входящий закрыть» → Egress-only Internet Gateway, а не NAT Gateway. Инстанс без DNS hostname в новой VPC → включи в VPC атрибуты DNS resolution и DNS hostnames.

Direct Connect

  • Private VIF — к ресурсам в VPC (через VGW или DX Gateway). Public VIF — к публичным сервисам AWS (S3). Transit VIF — к Transit Gateway.
  • Direct Connect Gateway — один канал к VPC в нескольких Regions.
  • Шифрование: VPN поверх DX (IPsec over public VIF) или MACsec.
  • Резервирование: второй DX (другая локация) или VPN как backup. Максимальная отказоустойчивость — 2 DX в 2 локациях.
  • Данные по DX: DataSync agent через service/VPC endpoint на private VIF (трафик не идёт в интернет).

VPC endpoints

  • Gateway endpoint — только S3 и DynamoDB, бесплатно, запись в route table.
  • Interface endpoint (PrivateLink) — ENI с private IP в твоей подсети для остальных сервисов и для чужих сервисов; платно.
  • PrivateLink также публикует твой сервис другим VPC без peering (за NLB).

Route 53 средне

  • Типы записей: A, AAAA, CNAME (не для корня зоны), Alias (бесплатно, для корня зоны, к ELB, CloudFront, S3 website, API Gateway; не к EC2 DNS).
  • Health checks + failover routing: primary/secondary. Health check умеет проверять endpoint, другие health checks (calculated) и CloudWatch alarm.

Route 53 только направляет DNSОн не обрабатывает данные, не видит HTTP-заголовки и не ускоряет трафик. Для «обработать рядом с пользователем» нужен edge compute.

CloudFront и Global Accelerator средне

  • CloudFront — CDN: кэш статики и динамики на edge. Origins: S3, ALB, EC2, любой HTTP. OAC (Origin Access Control) закрывает S3 так, чтобы доступ был только через CloudFront. HTTPS с ACM-сертификатом из us-east-1.
  • Приватный контент: signed URLs (отдельный файл, клиенты без cookies) или signed cookies (много файлов), + OAC на origin. S3 presigned URL обходит CloudFront.
  • Geo restriction, WAF, Shield, origin failover (origin groups), field-level encryption.
  • Edge compute: Lambda@Edge (viewer/origin request и response, полноценный код) и CloudFront Functions (только viewer, очень лёгкая логика: заголовки, редиректы). Response headers policy только добавляет/меняет заголовки ответа.
  • Global Accelerator — 2 anycast IP, трафик идёт по сети AWS, быстрый failover по health. Для TCP/UDP и не кэширует (игры, VoIP, статические IP, быстрый регион-failover). CloudFront — для HTTP-кэша.
⚠ Ты ошибался здесьГлобальный real-time clickstream, обработка у пользователя: CloudFront + Lambda@Edge + Kinesis + S3. Route 53 latency/geoproximity лишь направляет DNS; Athena не обрабатывает потоки.

6. Отказоустойчивость, decoupling и DR

Принципы HA

  • High availability = работает при отказе компонента: ≥ 2 AZ, нет single point of failure. Disaster recovery = восстановление после отказа Region/всего окружения.
  • Stateless приложение: сессии в ElastiCache/DynamoDB, файлы в S3/EFS — тогда инстансы заменимы.
  • Состояние внутри инстанса (EBS, instance store) мешает масштабированию и HA.

Auto Scaling Group

  • min / desired / max, размещение в нескольких AZ, замена нездоровых инстансов (EC2 и ELB health checks).
  • Launch template (версии) — новый AMI = новая версия шаблона; существующие инстансы обновляет instance refresh.
  • Политики: target tracking (держи метрику ≈ значению, проще всего), step, simple, scheduled (известная нагрузка), predictive. Метрики: CPU, ALBRequestCountPerTarget, длина очереди SQS на инстанс.
  • Lifecycle hooks — действие при запуске/остановке; warm pool — предподготовленные инстансы для быстрого старта; cooldown.

Какие данные как реплицировать

  • S3: Cross-Region Replication (нужен versioning; реплицирует только новые объекты, для старых — Batch Replication). Lifecycle в Glacier и копии на EC2 данные между Regions не переносят.
  • RDS: Multi-AZ = HA в Region (синхронный standby, авто-failover, не для чтения); cross-Region read replica → можно повысить (promote).
  • Aurora Global Database: репликация < 1 с, RTO < 1 мин при promote вторичного Region.

EBS: Data Lifecycle Manager или AWS Backup? «Автоматические snapshots EBS по расписанию» с минимумом настроек → DLM (бесплатно, по тегам). Много сервисов/аккаунтов или compliance → AWS Backup.

DMS и SCT

  • DMS: миграция БД с минимальным простоем; CDC (непрерывная репликация изменений) после полной загрузки. Источник остаётся рабочим. Нужен replication instance.

DataSync против Storage Gateway средне

  • DataSync — управляемое копирование NFS/SMB/HDFS/S3 → S3, EFS, FSx в обе стороны; расписание, проверка целостности, throttling, до 10× быстрее ручных инструментов. Агент on-prem. Через Direct Connect агент работает через VPC/service endpoint на private VIF.

⚠ Ты ошибался здесь«Полностью управляемая, автоматическая и ускоренная репликация данных в AWS-хранилища по Direct Connect» → DataSync через service endpoint. File gateway — это файловая шара для приложений, tape gateway — виртуальная лента.

Snow Family

Физические устройства для офлайн-переноса: Snowcone (малый, 8–14 ТБ), Snowball Edge (storage optimized ~80 ТБ, compute optimized) и вычисления на периферии. RDS и Aurora

  • Multi-AZ — синхронный standby в другой AZ, авто-failover, для HA (не для чтения). Read replica — асинхронная, масштабирование чтения, можно в другом Region.

  • RDS Proxy — пул соединений: спасает от шторма подключений Lambda, ускоряет failover.
  • Aurora: хранилище до 128 ТиБ, 6 копий в 3 AZ, быстрый failover; Aurora Serverless v2 — автоматическое масштабирование ёмкости; Global Database — репликация в другие Regions < 1 с, быстрый promote при аварии; Backtrack (откат во времени, MySQL).
  • Миграция provisioned Aurora → Serverless v2: добавить Serverless-экземпляр в кластер, failover на него.
  • IAM database authentication, шифрование при создании, SG на порт БД.

DynamoDB слабо

  • Режимы ёмкости: provisioned (+ auto scaling) и on-demand (непредсказуемо). Ключ: partition key (+ sort key). Горячий ключ — антипаттерн.

  • DAX — in-memory кэш только для DynamoDB, микросекунды, без изменения кода приложения (вместо ElastiCache/API Gateway cache).
  • TTL — автоудаление; PITR — 35 дней; Global Tables — multi-Region multi-active.
  • DynamoDB Streams — упорядоченный поток изменений (24 ч); с Lambda (event source mapping) — реакция на новые/изменённые элементы.
  • Транзакции (ACID, TransactWrite), условные записи.

11. Стоимость

Где экономить

  • Compute: стабильная база — Savings Plans/RI; прерываемое — Spot; нерегулярное — On-Demand; нагрузка по расписанию — scheduled scaling и Instance Scheduler; Compute Optimizer предлагает right-sizing.
  • Serverless: платишь только за использование (Lambda, Fargate, DynamoDB on-demand, Aurora Serverless).
  • Хранение: подходящий класс S3, lifecycle, Intelligent-Tiering при неизвестном доступе; EBS gp3 вместо gp2; удалять неприкреплённые тома, старые snapshots, неиспользуемые EIP.
  • Передача данных: вход бесплатен; выход в интернет платный; между AZ платно; в одной AZ по private IP бесплатно; через VPC Gateway endpoint к S3/DynamoDB без платы NAT. CloudFront дешевле прямой раздачи с S3/EC2.
  • NAT Gateway стоит дорого (почасовая + за ГБ): трафик к S3/DynamoDB пускай идёт через Gateway endpoint.

Серверно и бессерверно по цене

Типовые «most cost-effective»
  • Нерегулярная короткая нагрузка → Lambda, а не EC2.
  • Устойчивая нагрузка 24/7 на 1–3 года → Savings Plans/Reserved.
  • Отказоустойчивый batch → Spot (+ Spot Fleet/ASG mixed).
  • Редкий доступ к данным → S3 IA/Glacier; неизвестный → Intelligent-Tiering.
  • Раздача статики → CloudFront + S3, не EC2.

Топ ловушек экзамена

  1. Выдуманные ресурсы («Spot volumes», «SR-IOV volumes»): сомневаешься — вычёркивай.
  2. Region-границы: ACM, snapshots, AMI, KMS-ключи, TGW, S3 CRR.
  3. Route 53 не обрабатывает данные, только направляет DNS.
  4. SCP не даёт прав, а только ограничивает.
  5. Multi-AZ ≠ DR: для аварии региона нужен другой Region.
  6. gp3 без Multi-Attach; EBS в одной AZ; EFS — между AZ.
  7. NAT Gateway в public subnet; в private только маршрут на него.
  8. Athena ≠ real-time, Kinesis ≠ SQL по S3.
  9. Config = состояние, CloudTrail = действия, CloudWatch = метрики/логи.
  10. Instance store пропадает, EBS остаётся.
  11. «Минимум усилий» → managed/serverless; «минимум стоимости» → Spot/SP/IA; «real-time» → Kinesis.

Что выбрать: сравнения в одну строку

  • SQS очередь (pull) · SNS рассылка (push) · EventBridge события AWS и расписание · Kinesis поток.
  • ALB HTTP · NLB TCP/статический IP · GWLB appliances.
  • CloudFront кэш HTTP · Global Accelerator TCP/UDP anycast без кэша.
  • Secrets Manager ротация · Parameter Store конфиги · KMS ключи · CloudHSM свой HSM.
  • GuardDuty угрозы · Inspector уязвимости · Macie PII в S3 · Security Hub сводка.
  • WAF L7 · Shield DDoS · NACL подсеть stateless · SG инстанс stateful.
  • Peering 1:1 · TGW hub · PrivateLink сервис без peering · VPN быстро · DX выделенный канал.
  • RDS Multi-AZ HA · read replica чтение · Aurora Global DR между Regions.
  • EBS блок · EFS Linux-шара · FSx Windows/Lustre · S3 объекты.
