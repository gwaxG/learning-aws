3. Идентичность и доступ: IAM, Organizations

IAM: основы

  • User — долгоживущая личность (пароль, access keys). Group — набор users (в группу нельзя вложить группу, группа не может быть principal). Role — временные credentials через STS, без постоянных ключей.
  • Policy — JSON: Effect, Action, Resource, Condition. Identity-based (на user/role) и resource-based (S3 bucket policy, KMS key policy, SQS, trust policy роли).
  • Для EC2, Lambda, ECS всегда role (instance profile), никогда ключи в коде или AMI.
  • Root: MFA, нет ключей, использовать только для задач, требующих root.
Логика вычисления политик
  1. По умолчанию всё запрещено (implicit deny).
  2. Любой explicit Deny побеждает всё.
  3. Иначе нужен хотя бы один Allow.
SCP и permission boundary только ограничивают максимум и сами ничего не разрешают: итог — пересечение.
⚠ Ты ошибался здесьMFA на группу пользователей и Parameter Store против Secrets Manager. Политика ключа KMS против прав роли: чтобы роль могла использовать ключ, нужны оба — key policy допускает (или делегирует IAM), и IAM-политика роли разрешает.

Кросс-аккаунтный доступ

В аккаунте B создай role с trust policy на аккаунт A; в A пользователь получает право sts:AssumeRole. Временные credentials, без обмена ключами. Для внешних сторон добавляй ExternalId.

Federation

  • IAM Identity Center (бывший SSO) — вход сотрудников во все аккаунты Organization из корпоративного IdP.
  • Cognito — пользователи твоего приложения (User Pool = каталог и токены, Identity Pool = временные AWS credentials).
  • SAML 2.0 / OIDC federation — прямой вход в консоль через IdP.

Organizations и multi-account слабо

Organizations: управляющий аккаунт, организационные единицы (OU) и member-аккаунты. Даёт consolidated billing (общий счёт, объёмные скидки, общее покрытие RI/Savings Plans) и централизованное управление через SCP.

  • SCP — потолок прав для аккаунтов и OU. Не выдаёт права, не действует на management account, действует на root user member-аккаунта. Типичные SCP: запрет выхода из Region, запрет отключать CloudTrail/Config, запрет root.
  • Control Tower — готовая landing zone: multi-account среда по best practice, Account Factory создаёт аккаунты по шаблону, guardrails (preventive = SCP, detective = Config rules), dashboard несоответствий. Ответ на «настроить и управлять multi-account окружением с наименьшими усилиями».
  • RAM — делится ресурсами (подсети, TGW, License Manager configs) между аккаунтами без копирования.
  • Организационный CloudTrail — один trail для всех аккаунтов; Config aggregator — сводный вид соответствия.
  • Delegated administrator — сервис (GuardDuty, Security Hub, Config) администрируется из отдельного security-аккаунта.
Модель «много аккаунтов»Отдельные аккаунты: prod/dev, log archive, security/audit, shared services (сеть). Граница аккаунта — самая сильная граница безопасности и биллинга. Если спрашивают «изолировать» — новый аккаунт, а не новый VPC.
⚠ Ты ошибался здесьВопрос про landing zone с dashboard несоответствия → Control Tower (Account Factory + guardrails), а не ручная Organizations + Config. SCP не даёт прав: без IAM-политики доступа всё равно нет.

Доступ для приложений и ресурсов

  • S3 bucket policy — resource-based, умеет Deny по условиям (aws:SecureTransport, aws:SourceVpce, org id).
  • Presigned URL — временный доступ к объекту от имени создателя.
  • Permission boundary — максимум прав, который IAM-админ может делегировать пользователю/роли.
  • Access Analyzer — находит ресурсы, доступные извне, и неиспользуемые права.
  • Credential report / last used — аудит ключей и паролей.
