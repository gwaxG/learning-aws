# CLAUDE.md — AWS SAA-C03 Trainer

Personal offline study trainer for **AWS Certified Solutions Architect – Associate (SAA-C03)**.
Static site: vanilla JS (ES modules), no build step, no dependencies; all content is JSON under `content/`.
Progress is stored in the browser's `localStorage`.

## Language
- Everything is in **English** (UI, notes, labs, questions, explanations, services map, hub cards).
- Questions the user sends are stored **verbatim** (stem and options exactly as given).

## Run & check (all commands from `site/`; the repo root also has `infra/`, see below)
```bash
node serve.js                        # http://localhost:8000
node --test                          # unit tests (quiz, storage, hub-lib, flashcards)
node scripts/build-hub.mjs           # rebuild content/hub/index.json (after ANY hub card or question change)
node scripts/build-flashcards.mjs   # regenerate content/flashcards/cards.json (after ANY services.json change)
node scripts/validate-content.mjs    # validate all content, incl. both maps, index.json and cards.json freshness
node scripts/list-services.mjs [str] # service-id vocabulary of map #1 (optional filter)
```
**After any content change:** `node scripts/build-hub.mjs && node scripts/build-flashcards.mjs && node scripts/validate-content.mjs && node --test`.
Question text from topics/exams is copied into `index.json`, so editing a question also requires a rebuild.

## Map #1 — services (`content/maps/services.json`)
`categories[] → { id, name, summary, services[] }`, service:
```json
{ "id": "sqs", "name": "Amazon SQS", "tagline": "what it is, ≤80 chars",
  "facts": ["3–6 exam facts/limits"], "use_when": ["2–4 'choose when…' triggers"],
  "not_for": ["0–3 traps"], "vs": [{ "id": "sns", "note": "difference, ≤100 chars" }],
  "keywords": ["4–10 search terms"], "doc": "https://docs.aws.amazon.com/..." }
```
- `id` is stable kebab-case — **never rename** (hub cards reference it).
- `vs[].id` must exist. Concepts (dr-strategies, rto-rpo, decoupling, encryption…) are "services" in the `concepts` category.
- UI: radial mind map (wheel zoom, drag pan), search highlighting, click → card with "Hub questions: N";
  "Cheat sheet" tab shows cards by category (printable).

## Weak points (`#/weak-points`)

- `content/weak/weak-points.json` is hand-authored: `diagnostic` (date, asked, correct, results[{area|null, q, ok, answer?}]) and `areas[]` (`id, title, severity 1-3, why, evidence[], rules[], theory[{topic, heading}], services[]`).
- Theory is pulled live from topic essentials (`heading` must match exactly); flashcards for an area are all cards of its `services` (`#/flashcards?w=<id>`); questions come from hub docs whose `services` overlap (user-sourced shown first). Do not copy cards or theory into this file.
- Update it when the user finishes a new diagnostic or when a repeated miss shows up in ingestion: adjust `severity`, add `evidence`/`rules`, keep `diagnostic.asked/correct` equal to `results`. The validator checks service ids, topic headings and counts.
- Keep evidence honest: say how thin the signal is (a 10-question diagnostic with one miss is a weak signal).

## Flashcards (`#/flashcards`)
Short fact cards, **generated** from map #1 (one source of truth — never write cards for a service by hand):
Purpose (tagline), Which service? (reverse), When to use (`use_when`), Key facts (`facts`),
Numbers & limits (cloze from facts with number+unit), Not for / traps (`not_for`), Compare (each `vs` note).
Card id = `<service>:<type>[:n]` (stable while the service id and fact order are stable).
- Extra facts that don't fit a service field → `content/flashcards/extra.json`: `{ "id": "kebab", "service": "<id>", "q": "...", "a": "..." }`.
- Progress: `store.recordCard/getCard` — Leitner box 1..3 (known → +1, unknown → 1); "To learn" mode hides box 3.
- Reordering `facts` renumbers cloze card ids (progress for those cards resets) — append new facts instead.

## Map #2 — question hub (`content/hub/docs/*.json`)
Every question is a knowledge card. For topic/exam questions the question text is **not copied** —
`build-hub.mjs` pulls stem/options/answer/explanation from the source by `id`.
```json
{
  "id": "sto-q1",
  "source": { "type": "topic", "ref": "storage" },
  "concept": "S3 Lifecycle: storage class cascade matching access pattern",
  "tests": "What the question actually tests (1–2 sentences).",
  "expected": "Expected answer in your own words + trigger words in the stem that point to it.",
  "why_not": "Why the main distractors are wrong.",
  "keywords": ["lifecycle", "Glacier Deep Archive", "compliance", "12 hours"],
  "services": ["s3-lifecycle", "s3-storage-classes", "glacier"],
  "topics": ["storage", "cost"],
  "domain": 4,
  "related": []
}
```
- `concept` — style "Service/area: gist", ≤ 90 chars. **Reuse existing wording verbatim** when it is the same idea
  (the UI groups identical concepts under "Most frequent concepts"). List existing ones:
  `node -e 'console.log(Object.keys(require("./content/hub/index.json").byConcept).join("\n"))' | grep -i <word>`.
- `services` — 1–5 ids from map #1, primary service first (it anchors the node on the graph).
- `topics` — manifest slugs (1–3). `domain` 1–4 (Secure / Resilient / High-Performing / Cost-Optimized).
- `related` — optional manual links (other doc ids); up to 6 automatic links are computed in `buildIndex`
  from shared services, concept, keywords and topics.
- UI: questions ↔ services graph; a keyword/chip highlights matching questions (keywords/concept = strong match,
  mention in text = weak), their services and related questions; click a question → card (self-check, concept,
  expected answer, links); click a service → filter.

## Workflow: the user sends a new question
Andrei sends questions while preparing (text or screenshot) — "ingest". For each one: ingest → enrich the services map → enrich topics → rebuild:
1. **Duplicates:** search key phrases in `content/hub/docs/` and `index.json`. If it already exists, say so and
   don't create a copy (you may enrich `keywords`/`related` of the existing card).
2. **Card** `content/hub/docs/u-YYYYMMDD-<short-slug>.json` (date = day added):
   ```json
   {
     "id": "u-20260927-s3-object-lock",
     "source": { "type": "user", "added": "2026-09-27", "origin": "where it came from, if stated" },
     "question": {
       "stem": "Question text exactly as sent",
       "options": ["...", "..."],
       "answer": 1,
       "explanation": "Why the correct answer is correct and why the others are not"
     },
     "concept": "...", "tests": "...", "expected": "...", "why_not": "...",
     "keywords": [], "services": [], "topics": [], "domain": 1, "related": []
   }
   ```
   `answer` is a 0-based index or an array for multi-select. If the user didn't give the answer, determine it and
   say so explicitly; if the question is debatable, note it in `explanation`.
2b. **Weak points (default for pasted questions).** The user now sends only questions he FAILED, so every ingested question is a miss:
   add it to `content/weak/weak-points.json` — pick the matching area (or create a new area when none fits), append a short `evidence` line
   ("Missed: <topic of the question>"), add or sharpen a `rule` (one line) for the trap, add a `theory` item if a relevant topic essential
   is missing, add the services to `services`, and raise `severity` when the same area keeps getting missed (3+ misses → 3).
   Do not copy the question itself: the area page lists hub cards by service overlap and flashcards by service.
3. **Enrich map #1** if needed (flashcards are regenerated from it in step 6): new service → add to the right category with all fields (new stable `id`);
   new exam fact/trap/"vs" pair → append to the existing service (concise, no duplicates). Never delete or rename ids.
4. **Enrich topics** (on every ingestion, if applicable): find the relevant `content/topics/<slug>.json`
   essential(s) and add any exam fact, trap or distinction the question tests that is not yet covered —
   usually one or two sentences appended to the **How.**/**Exam.** part of the matching essential (keep the
   What/Why/How/Exam format), plus an official AWS doc link in `links` when useful. If no essential fits, add a
   new one. Don't duplicate what's already there; don't touch `cli`/`pulumi` or existing questions.
   Edit topic files with minimal targeted text edits (not a full json.dump rewrite) to keep diffs small and
   preserve formatting/line endings.
5. **Enrich related hub cards** if the new question adds a useful angle (extra `keywords` / manual `related`).
6. `node scripts/build-hub.mjs && node scripts/build-flashcards.mjs && node scripts/validate-content.mjs && node --test`.
7. Reply in **Russian** (AWS terms stay in English), explaining from the basics — assume the reader is not yet
   fluent in the topic. Structure:
   - **Ответ:** the correct option(s), one line.
   - **Why / What / How** — one line each: why (the need/trigger in the stem), what (the service/feature),
     how (how it solves it).
   - **База** — short sections that teach the underlying concepts the question relies on, from zero:
     how the thing actually works (e.g. how traffic flows, what a route table entry looks like, what a NACL rule can
     contain), with tiny concrete examples (a route table line, a rule, a flow like `Pod → NAT → IGW → service`) and
     a comparison table when there are 2–3 similar options (e.g. on-demand backup vs PITR vs AWS Backup).
   - **Разбор неправильных вариантов** — one short block per wrong option: quote what it proposes, then explain
     *each* mistake in it concretely (what is impossible / what requirement it misses / which property it confuses),
     calling out deliberate traps (swapped properties, irrelevant distractor services, noise in the stem).
   - **Как быстро распознавать** — 3–6 bullets `trigger phrase → answer` / `phrase in option → error`.
   - Footer (after `---`): card id, what changed in the services map and topics, top related questions,
     validation status, commit status.
   Keep it dense: no filler, no repetition; tables and code-style snippets over long prose.
   **Always** include why each wrong option is wrong, even when the user asks for a short answer (one line per option).

## Change rules
- Don't reorder `options` of existing questions (`answer` and saved progress depend on it).
- Never edit `content/hub/index.json` by hand — only via `build-hub.mjs`.
- Don't rename existing ids (questions, services, labs): localStorage progress and the hub reference them.
- New diagrams: offline SVG in `content/diagrams/`, dark background (#0f1b2d).
- Practice questions are original, SAA-C03 style — not real exam questions.

## Deployment (`infra/`, `.github/workflows/learning-aws-deploy.yml`)
The repo root holds `site/` (this trainer, everything above) and `infra/` (Pulumi, Python): S3 + CloudFront + ACM + Route 53 publishing `site/`.
Only `index.html`, `css/`, `js/`, `content/` (not `content/hub/docs/`) and `book/saa-c03-book.html` are uploaded.
Setup, config keys (`domain`, `zoneName`, `createZone`, `basicAuth`, `siteDir`) and the OIDC role: `infra/README.md`.
Merge to main/master: site tests + infra tests, then `pulumi up` (only when the repo variable `DEPLOY_ENABLED=true`). Infra tests: `cd infra && uv run --python 3.12 pytest`.
After adding a published file type/folder to the site, update `PUBLISH_DIRS`/`PUBLISH_FILES` in `infra/__main__.py`.
